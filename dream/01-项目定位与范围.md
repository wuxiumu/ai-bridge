# 01｜项目定位与范围

## 1.1 一句话定义

`ai-bridge` 是一个**可自部署的 AI Gateway（OpenAI Compatible API Hub）**：对外提供 OpenAI 兼容 API，对内对接多个模型与多把 Key，并具备生产可用的安全、观测与运维能力。

## 1.2 解决的问题（Why）

- 跨地域/跨网络环境访问模型困难：用一台可访问上游的服务器对外提供统一入口。
- 多模型并存与迁移成本高：同一套 OpenAI 兼容接口，接入不同 Provider。
- Key 管理混乱：Key 轮换、故障切换、限流与日志审计。

## 1.3 目标用户（Who）

- Dify / 自研 Agent 平台用户：需要「自定义 OpenAI 兼容」网关。
- 国内团队/企业：希望统一对外出口、可控的 Key 与用量。
- 多模型使用者：希望按成本/质量/可用性进行路由。

## 1.4 产品边界（Scope）

### In scope（本项目要做）

- OpenAI Compatible API（至少覆盖 `/v1/models`、`/v1/chat/completions`）
- 多模型配置与路由（MVP 先静态配置）
- 多 Key 管理（MVP 可先“多模型条目绑定不同 Key”；产品化后做轮换/Failover）
- 基础安全：鉴权（Master Key）、HTTPS（通过 Nginx/反代）
- 基础观测：请求日志、上游错误、（可选）Token 用量统计
- 一键部署：脚本（MVP）→ Docker Compose（产品化）

### Out of scope（暂不做/明确不做）

- 浏览器端 UI（Dashboard）作为第一阶段交付物
- 复杂计费/账单系统
- 取代上游 Provider 的权限/合规模块（本项目只做代理与治理）

## 1.5 设计原则（How）

- **OpenAI 兼容优先**：客户端无需改代码或最少改动（Base URL + Key）。
- **先 MVP 可跑通**：文档清晰、30 秒启动、可被 Dify 直接使用。
- **生产化渐进**：Docker、TLS、限流、监控逐步叠加。
- **可运维**：每个能力都要能被观测/回滚/降级。
