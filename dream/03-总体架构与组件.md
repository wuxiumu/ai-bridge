# 03｜总体架构与组件

## 3.1 目标架构（文本图）

```
Client (curl / Dify / App)
        |
        |  HTTPS (可选)
        v
Reverse Proxy (Nginx，可选但推荐)
        |
        |  HTTP
        v
AI Gateway (LiteLLM Proxy 为核心)
        |
        |  Provider SDK / HTTPS
        v
Upstreams (OpenAI / Anthropic / Gemini / DeepSeek / Azure ...)
```

可选公网暴露方式：

```
Client -> Cloudflare Tunnel -> Nginx -> Gateway -> Upstreams
```

## 3.2 组件职责

### Client

- 配置 `Base URL` 指向网关
- 携带 `Authorization: Bearer <master_key>`
- 使用网关暴露的 `model` 名称

### Nginx（建议产品化阶段启用）

- TLS 终止（HTTPS）
- 基础限流（`limit_req`）
- IP 白名单/地理封禁（可选）
- 访问日志（可用于审计/溯源）

### Gateway（LiteLLM Proxy）

- 提供 OpenAI 兼容接口
- 解析 `model` 并路由到上游
- 统一鉴权（master key）
- 记录请求日志与（可选）token 用量
- 执行 Key 轮换与 Failover（产品化增强）

### Upstreams（多 Provider）

- 实际执行推理
- 可能返回 429/5xx/超时等，需要网关处理重试/切换/降级

## 3.3 请求流程（关键点）

1. 客户端向 `POST /v1/chat/completions` 发起请求
2. 反代（如启用）做 TLS、限流、基础访问控制
3. 网关鉴权（master key）
4. 网关根据 `model` 选择上游（以及 Key/实例）
5. 上游返回结果；网关将响应转换/透传为 OpenAI 兼容格式
6. 网关记录：耗时、状态、模型、上游、（可选）token 用量

## 3.4 失败场景与治理策略（概览）

- 429（限流/配额）：切换 Key；必要时降级模型（Failover）
- 5xx/超时：重试或切换上游/模型
- 单点故障：容器重启/进程守护；日志与健康检查用于自动恢复
